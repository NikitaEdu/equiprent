# Навантажувальне тестування та тестування обсягом даних

Сценарії запускаються проти робочого екземпляра застосунку з демонстраційними даними
(див. кореневий README). Результати зберігаються в `results/` у форматі JSON.

```bash
npm ci
node read-scenario.mjs            # читання каталогу й календаря: 5, 10, 25 VU; прогрівання 60 с; по 180 с
node write-scenario.mjs           # створення бронювань: 10 VU, 60 с; перевірка інваріанта в БД
node volume.mjs 100               # тест обсягом: 100 / 1000 / 10000 бронювань (запускати по черзі)
```

Змінні: `BASE_URL` (типово http://localhost:8080), `DURATION`, `WARMUP`, `LEVELS`, `CONNECTIONS`,
`PGURL` (для перевірок у БД; типово `postgresql://postgres@localhost:5432/rental`).

Генератор (`generator.mjs`) реалізує закриту модель: кожен віртуальний користувач надсилає наступний запит
одразу після відповіді. Віртуальний користувач не тотожний реальному відвідувачу: реальні користувачі
роблять паузи, тож одержані значення — оцінка для найгіршого випадку на цьому стенді.

Перевірка узгодженості вимірювань: `littleLawConcurrency = rps × середня затримка` має наближатися до
кількості VU. Інструмент autocannon 9.0 на навчальному стенді цю перевірку не пройшов
(`results/autocannon-rejected-read-scenario.json`), тому використано власний генератор.

Перевірка збереження даних після перезапуску (NFR-DATA-02): `node persist-check.mjs`.
На Linux/macOS застосунок перезапускається скриптом `restart-app.sh`; на Windows скрипт попросить зупинити
й знову запустити застосунок вручну і дочекається його готовності. Власну команду перезапуску можна задати
змінною `RESTART_CMD` (наприклад, `RESTART_CMD="docker compose restart app"`).

**Навантаження створюйте лише на власному стенді.**
