# Інструкція адміністратора EquipRent

## Розгортання

Система — один застосунок Spring Boot (віддає і REST API, і зібраний інтерфейс React) та база PostgreSQL 16.
Рекомендований спосіб — `docker compose up --build` (див. README). Порти: застосунок — 8080/TCP.
База в `docker-compose.yml` назовні не публікується; застосунок звертається до неї внутрішньою мережею Compose.

Для публічного стенда:
- розмістіть застосунок за зворотним проксі з HTTPS і встановіть `COOKIE_SECURE=true`;
- не відкривайте порт PostgreSQL в інтернет;
- задайте `SEED_DEMO_DATA=false`, щоб не створювати демонстраційних облікових записів з відомими паролями.

## Конфігурація

Усі параметри задаються змінними середовища (перелік — у README). Секрети (`DB_PASSWORD`) зберігаються у
файлі `.env` поруч із `docker-compose.yml`, який не додається до репозиторію. Приклад без секретів — `.env.example`.

## Схема даних і міграції

Міграції Flyway розміщено в `backend/src/main/resources/db/migration`. Вони виконуються автоматично під час
старту застосунку; історія — таблиця `flyway_schema_history`. Hibernate працює в режимі `validate`:
якщо схема не відповідає сутностям, застосунок не стартує й повідомляє причину в журналі.

Розширення PostgreSQL `btree_gist` і `pg_trgm` створюються першою міграцією. Вони належать до довірених
(trusted) розширень, тож власник бази може створити їх без прав суперкористувача.

## Створення облікового запису менеджера

Самостійна реєстрація завжди створює роль «клієнт». Щоб надати роль менеджера наявному користувачу,
виконайте в базі (замініть адресу):

```sql
UPDATE app_user SET role = 'MANAGER' WHERE lower(email) = lower('ім''я@приклад.ua');
```

Зміна набуває чинності після наступного входу користувача.

## Журнали та діагностика

- Docker: `docker compose logs -f app`; локальний запуск — стандартний вивід процесу.
- Кожен рядок журналу містить ідентифікатор запиту у квадратних дужках; цей самий ідентифікатор
  повертається клієнту в заголовку `X-Request-Id`. Знайдіть рядок за ідентифікатором, щоб відтворити шлях запиту.
- Паролі, токени й тіла форм у журнал не записуються.
- Стан: `/actuator/health/liveness` (процес живий) та `/actuator/health/readiness` (готовий, база доступна).
  Метрики (`/actuator/metrics`) доступні лише ролі «менеджер».

Приклад діагностики, виконаний під час розробки (див. журнал дефектів, DEF-01): застосунок не стартував,
у журналі — `FATAL: invalid value for parameter "TimeZone": "Europe/Kiev"`. Причина — застаріле ім'я
часового поясу ОС. Виправлення — процес працює в UTC, а бізнес-дата визначається параметром `APP_TIMEZONE`.

## Резервне копіювання та відновлення

Резервна копія (Docker):
```bash
docker compose exec -T db pg_dump -U rental -d rental -Fc > equiprent-$(date +%F).dump
```
Відновлення **на окремому навчальному середовищі** (не на робочій базі):
```bash
docker compose exec -T db pg_restore -U rental -d rental --clean --if-exists < equiprent-2026-12-01.dump
```
> Увага: `--clean` видаляє наявні об'єкти бази перед відновленням.

## Небезпечні операції

| Операція | Наслідок |
|---|---|
| `docker compose down -v` | безповоротно видаляє том із даними бази |
| Зміна вже застосованої міграції | Flyway відмовиться стартувати (контрольна сума); створюйте нову міграцію `V2__…` |
| Запуск інтеграційних тестів із `TEST_DB_URL`, що вказує на робочу базу | тести очищують таблиці — дані буде втрачено |

## Оновлення версії

1. Отримайте код потрібного релізу (`git checkout v1.0.0`).
2. Зробіть резервну копію бази.
3. `docker compose up --build -d` — нові міграції застосуються автоматично.
4. Перевірте `/actuator/health/readiness` і основний сценарій.
