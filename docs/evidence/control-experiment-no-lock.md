# Контрольний експеримент: тести конкурентності без песимістичного блокування

Дата: 22.11.2026. Стенд: див. loadtest/results/*.json (environment).

Зміна (тимчасова, не зафіксована в репозиторії): в `EquipmentUnitRepository.lockAvailableByType`
вимкнено анотацію `@Lock(LockModeType.PESSIMISTIC_WRITE)`, тобто вибірка екземплярів виконувалася без `FOR UPDATE`.
Обмеження `ex_booking_unit_no_overlap` (EXCLUDE) залишалося.

Команда: `mvn verify -Dit.test=ConcurrencyIT -Dtest=NoSuchTest -Dsurefire.failIfNoSpecifiedTests=false`

| Тест | Результат без блокування | Пояснення |
|------|--------------------------|-----------|
| TC-CONC-01 (10 запитів, 1 екземпляр) | пройдено | 9 вставлень відхилено обмеженням EXCLUDE (SQLSTATE 23P01) і перетворено на 409 |
| TC-CONC-02 (12 запитів, 3 екземпляри) | **не пройдено**: створено 1 бронювання замість 3 | усі транзакції одночасно бачили однакову зайнятість і обрали той самий екземпляр; БД відхилила 11 вставлень, хоча два екземпляри були вільні — хибні відмови |
| TC-CONC-03 (пряме вставлення перетину) | пройдено | не залежить від блокування |

У журналі запуску — 20 повідомлень `SQLState: 23P01`.

Висновок: обмеження бази даних забезпечує коректність (перетинів немає навіть без блокування),
а блокування потрібне для доступності — без нього клієнти отримують відмови за наявності вільних екземплярів.
Після експерименту файл відновлено; повний набір тестів пройдено.
